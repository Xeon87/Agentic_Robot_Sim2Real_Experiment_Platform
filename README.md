### 1. 放蛋判定（你那次放进去了，程序却判失败）
- **以前的判定**：只认两种证据：(a) 程序判断"槽被占"——槽格里的高度高于整个蛋托顶面 9 mm；(b) 在槽心 38 mm 内认出一个鸡蛋。但这只蛋托的尖角很高，鸡蛋立在槽里时露出的部分常常不够高；而且立着的鸡蛋多半不在 YOLO 的蛋托轮廓里，也不容易被认成鸡蛋，所以会漏判。
- **现在**（`[V4.6.8 VERIFY]`，满足任意一条就算放好）：
  1. **槽心比槽口高 8 mm 以上**：在蛋托周围**所有**深度像素里量（不只是 YOLO 的蛋托轮廓），空槽读数约 −13 mm（凹下去），立着鸡蛋约 +18 mm。
  2. 在槽心 0.5 个孔距内认出一个鸡蛋。
  3. **槽心比放蛋前高了 15 mm 以上**（和放蛋前那次识别直接对比）。
- 最多看 2 次（打开 Try harder 时 3 次）：第 1 次机械臂退回起点，第 2 次再抬高 100 mm。每次看到了什么证据都写进日志。
- 仿真里：0、1、2、6 个鸡蛋立在槽里的情况，每个槽是空是满都判断正确。

### 2. 连续抓 6 个鸡蛋，依次放进空槽
- 任务里写「全部入托」（或 Place all eggs… / 把所有鸡蛋… / 放满）就进入**连续模式**。每一轮：
  1. **重新识别**：已经立在蛋托里的鸡蛋不会被当成要抓的蛋，被占的槽不会再用。
  2. **先放离机械臂最远的空槽**，这样后面放蛋时夹爪不用从已经放好的蛋上方经过。
  3. 抓 → 转成竖直 → 插入 → 验证 → 回起点，然后下一轮。
  4. 桌上没有鸡蛋了，或者没有空槽了，就结束。没开 Try harder 时，失败 1 次就停；开了时最多容许 3 个鸡蛋放不成功。
- **夹爪不会顶到旁边的鸡蛋**：相邻两个槽中心只差 46–47 mm，两个鸡蛋之间只剩约 4 mm。规划放蛋姿态时，会检查两个夹爪指尖离旁边已立着的鸡蛋至少有 鸡蛋半径 + 6 mm，指向旁边鸡蛋的方向一律不用；这时会多试一些朝向（每 15° 一个）。
- **还要注意**：
  - 程序本来就不往离底座 28.5 cm 以内的槽放蛋（够不着），这样的槽会被跳过。
  - 鸡蛋放进槽后可能微微倾斜。
  - 连续 6 个鸡蛋大约需要几分钟。

### 3. 主相机监控上的标签
- 槽只显示**编号**（空槽绿色，有蛋橙色），鸡蛋显示 e1、e2…，蛋托显示「蛋托 2×3」。字体缩小一号，槽和蛋不再各画两遍标签。

### 4. Try harder（Agentic实机任务 页，「速度」下拉框左边的勾选框）
- 勾上之后，鸡蛋任务每一步失败时会换办法再试，而不是马上报失败：
  - **识别不完整**：让开视线后再看（最多 3 次）。
  - **规划失败**：换一个鸡蛋，或者换一个空槽（换槽是原有功能）。
  - **夹取失败**：张开夹爪 → 回起点 → 重新识别 → 重新规划 → 再夹（最多 3 次）。
  - **转向 / 插入没到位**（蛋还在夹爪里）：重新看一次蛋托，用新的坐标重新规划，先放回同一个槽，再试其他空槽（每个槽最多 2 次）。
  - **验证没看到**：多看一次（共 3 次）。
- 叠杯子的 LLM Agent 模式：会告诉 Agent"不要轻易放弃，失败时换策略"，可用的工具步数翻倍。
- 这个选项会保存，下次打开时保持。

### A. 蛋托定位（槽位偏得很远的主要原因）
- **原因**：你用的是 2×3（6 孔）蛋托，但上次 7 次识别**没有一次认成 2×3**，分别认成了 1×3、3×3、3×4。程序每次先量外框，再**猜**几行几列，把外框平均分格。量出的外框宽 128–149 mm，比 2×3 蛋托应有的约 118 mm 宽了约 30 mm（YOLO 轮廓多包进了东西），于是被猜成 3 行，多出来的"槽"落在不存在的位置上。你验证时选的 slot_1 / 3 / 4 / 5 里，很可能有这种假槽。
- **修改**：
  - `config/egg_carton.json` 写入你量的规格：`carton_grid: [2, 3]`，`slot_pitch_mm: [46, 47]`（沿 3 孔方向 46 mm，沿 2 孔方向 47 mm）。行列数和槽距固定，不再猜。
  - **固定模板拟合**：只求模板的位置和朝向。判据是"碗形"：每个槽口一圈比槽中间高。蛋托边缘的落差、桌面、多出来的平面都不算凹槽，这正是你担心的"把边缘当成凹槽"的问题。拟合前把 YOLO 轮廓内缩几个像素，去掉边缘的飞点和桌面点。
  - **编号固定**：沿 3 孔方向，离机械臂远的列编号大；蛋托转 180° 编号不变。
  - **诊断图**：每次识别蛋托都存一张图到 `cameracalib/carton_diag/`（保留最近 30 张）。左边是彩色画面，叠加 YOLO 轮廓（绿）、实际使用的内缩轮廓（青）和 6 个槽号；右边是高度图，标出每个槽的碗形分数和外框。
  - 日志新增一行 `[V4.6.6 CARTON] 固定模板 2×3 … 槽穴拟合（6/6 个碗形槽穴）… 每槽碗深 … 诊断图 …`。
- **仿真验证**：斜着看的 2×3 蛋托，YOLO 轮廓多包进 30 mm（外框量成 162×148 mm，和你的实测相近）。旧方法同样猜成 3×3；新方法 6 个槽在三种朝向下误差都 ≤ 1 mm。
- **你需要做的**：用「视觉精度验证」再测一次（① 只用主相机，6 个槽各测一次），填 dx / dy，并把 `cameracalib/carton_diag/` 里的诊断图发给我。如果日志显示「槽穴不清楚 → 模板按外框中心放置」，说明真实画面里的槽穴深度看不清，需要看图再调整。

### B. 闪退
- 上次（V4.6.5）是 Tk 主循环里的**段错误**，调用栈里没有任何我们自己的函数，现有日志无法知道是哪个 C 库崩的。

## V4.6.3
**V4.6.3**（热修复：V4.6.2 执行鸡蛋任务时控制台闪退）

### 这次闪退查到了什么
- `logs/crash.log`：`Fatal Python error: Aborted`，发生在**主线程**里 Tk 刷新「工作区安全」状态标签的 C 代码中（`NERO_V316 _status → configure`）。当时任务线程正在等机械臂下探到位，其他线程是两个相机采集、子进程输出读取和 CAN 监控，**崩溃那一刻都没有在操作界面**。
- 这是 C 层的 abort（不是 Python 异常）。Tcl / Xlib / glibc 在 abort 前会往终端打印一行真正的原因，但这一行以前**只出现在终端上**，`crash.log` 和 `console.log` 里都没有，所以现在还不能百分之百确定是哪个库。
- 用"探针"把所有 GUI 测试重跑了一遍，记录每一个**不在主线程**发起的 Tk 调用：发现实机管线、示教、关节运动等工作线程会通过 `real_cfg()` 直接读「实机NERO调试 → 参数」里的输入框（CAN 口、速度、固件等）。这种跨线程读取要排队等主线程；测试里还复现了它会卡住（主线程等工作线程时，工作线程的这次读取 5 秒都没返回）。这不是这次崩溃那一刻的直接原因，但属于同一类风险。之前 V4.5 那次启动时的段错误也发生在 Tk 的 C 代码里。

### 修改
1. **`real_cfg()` 只在主线程读界面**：工作线程拿到的是主线程最近一次的快照（每次轮询刷新，启动任务前也刷新）。重跑探针：实机任务、示教、关节控制路径上已经**没有任何跨线程 Tk 调用**（只剩冻结的 Camera 模块里手眼标定读标记设置的一处，不在任务路径上）。
2. **创建 Tk 窗口前调用 `XInitThreads`**：Xlib 变成线程安全的，任何第二个线程碰到 X 连接都不会再把进程 abort（`[xcb] Unknown sequence number … Assertion failed` 这一类）。libX11 1.8 起默认就这样做，Ubuntu 22.04 带的是 1.7.5。可用 `NERO_NO_XINITTHREADS=1` 关闭。
3. **X 错误不再让控制台消失**：你点「Smol VLA实机任务」那次闪退，crash.log 里**什么也没有**。这说明进程不是被信号杀死，而是 Xlib 遇到 X 错误后直接 `exit(1)`：这种退出只会在终端打几行字，faulthandler 抓不到（已在虚拟显示器上复现这种"无痕退出"）。V4.6.3 在创建窗口前装上自己的 X 错误处理：错误写进 `crash.log`（类型、请求号；请求号 139 = 字体 / 文字绘制），**控制台继续运行**。正常关闭时 crash.log 末尾会写 `console closed normally`，所以以后能分清是正常关闭、X 错误、abort 还是被系统杀掉（没有任何记录 = 被杀，例如内存不够）。
4. **C 层错误信息落盘**：`start_nero.sh` 把控制台的 stderr 同时写到终端和 `logs/stderr.log`（进程 abort 时也保留，已验证），并设置 `LIBC_FATAL_STDERR_=1`（glibc 的内存错误信息也进 stderr）；超过 5 MB 时转存为 `stderr.prev.log`。`crash.log` 开头会写一行 `XInitThreads ok`。

### 如果还闪退
请把 `logs/crash.log` 和 **`logs/stderr.log`** 一起发给我，stderr.log 最后几行就是 C 层的原因。如果 V4.6.2 那次的终端窗口还开着，也请把 `Aborted` 上面几行发给我。

## V4.5
**V4.5**（鸡蛋放进蛋托对不准 + 夹蛋时指尖碰桌面 + V4.4 闪退加固）
1. **放蛋对不准——找到并修好的原因**：
   - **夹着的鸡蛋位置用错了（主要原因，约 12 mm）**：夹蛋时鸡蛋被动爪推到固定爪上，蛋心离固定爪面约 20 mm；V4.3/V4.4 放蛋时却按 8.5 mm 补偿。V4.5 在夹蛋那一刻记下“蛋心在夹爪坐标系里的实际位置”（离线替身实测 (0, 20.3, 0) mm），放蛋时用同一个量。
   - **对准的是蛋心，不是先进槽的下端**：立蛋没到完全竖直时（以前从 −75° 开始试，倾斜 15°），下端会横向偏约 7 mm。V4.5 改为把**鸡蛋下端**对准槽心，倾斜多少都自动抵消；而且先试 −90° / +90°（真正竖直）。
   - **槽位按外框等分**：蛋托边沿、翻开的盖子会让外框变大，槽位整体偏移。V4.5 用深度图里每个空槽的“凹坑”找真实槽心，并据此拟合槽距和整体偏移（离线：外框偏 30 mm 时，旧算法最大偏 >10 mm，新算法 <2 mm）。可在 `config/egg_carton.json` 填实测槽距（用尺量相邻两槽中心距离），不填也能工作。日志里蛋托一行会显示“槽位按 N 个槽穴凹陷拟合：整体偏移 …，槽距 …”。
   - **放蛋前的腕部相机复查**：以前立蛋后腕部相机朝侧面，复查被跳过。V4.5 在转腕立蛋**之前**，夹爪朝下停在槽位正上方 12 cm，用腕部相机复测槽位；可信且偏差 1.5–15 mm 时按新位置重新规划下插。看不清（可能被夹着的鸡蛋挡住）或偏差过大时沿用主相机位置，日志会说明。
2. **指尖碰桌面——原因和修改**：
   - 安全区的 z 检查以前检查的是**胶垫中心**（下限 桌面 + 6/8 mm），而指尖在胶垫中心下面 10 mm，动爪张开时最多再低 1.5 mm——所以安全区实际允许指尖到桌面以下。V4.5 起检查点改为**最低的指尖**（固定爪 / 动爪、任意开口）：规划时要求离桌 ≥ 5 mm，执行时（所有 SO-101 任务的硬底线）≥ 3 mm。
   - 夹持高度：胶垫中心对准鸡蛋赤道（42 mm 蛋 → 21 mm），固定爪指尖离桌 11 mm、最低指尖 9.5 mm（以前 8.5 mm、且没检查）。小鸡蛋会自动抬高，保证指尖 ≥ 5 mm。
   - 桌面高度取“相机拟合桌面”和“安全区 z_table”中**更高**的那个；两者差超过 15 mm 时拒绝夹蛋（说明手眼标定或安全区桌面高度有问题），日志 `[FAIL] [V4.5 EGG PLAN] 相机测得的桌面比安全区 z_table …`。
