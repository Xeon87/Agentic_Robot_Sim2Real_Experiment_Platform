# NERO V4.8 — single-folder release

**V4.8 第 1 部分**（NERO 原装夹爪 AgxGripper：夹爪切换、pyAgxArm 驱动、「实机NERO调试 → 夹爪」页：状态 / 操作 / 校正归零 / 力控标定 / 示教模式测试 / J7 控制器限位）

V4.8 分三部分交付。这是第 1 部分。第 2 部分是工具模型（官方夹爪 STL + 腕部相机支架、TCP、碰撞）和 Agentic 杯子 / 鸡蛋任务的几何适配；第 3 部分是 Smol VLA 数据和仿真。

### 1. 夹爪切换（三个页面共用一个设置）
- 「实机NERO调试 → 夹爪」、「Agentic实机任务」夹爪区、「Smol VLA实机任务」示教夹爪行都有切换框：**SO-101** / **NERO 原装 AgxGripper**。切的是同一个设置，保存在 `config/gripper.json`。
- 录制中、任务运行中、夹爪页正在操作时不允许切换，会说明原因。
- 切换后日志列出接下来要做的事（重启驱动第 5/6 步、连接、归零、重做腕部和主相机手眼、示教负载约 0.56 kg）。

### 2. 控制方式：只用 pyAgxArm
- 选了原装夹爪时，ROS2 驱动**固定用 `effector_type:=none` 启动**，只有 pyAgxArm 一个程序发夹爪指令（CAN 0x159）。
- pyAgxArm 在一个单独的助手进程里运行（`NERO_V48_Gripper.py serve`），它只调夹爪的函数，`connect()` 不会发任何东西。
- 用的官方接口：`move_gripper_m(宽度 m, 力)`、`get_gripper_status()`、`disable_gripper()`、`reset_gripper()`、`calibrate_gripper()`、`get_gripper_teaching_pendant_param()`（读行程版本 70 / 100 mm）；J7 测试用 `get/set_joint_angle_vel_limits()`。
- 已用 AgileX 自己的虚拟 CAN 夹爪模拟器核对过：发出的帧是 0x159 `0000c350 05dc 01 00`（50 mm、1.5、使能 / 宽度模式），和 SDK 源码里的协议一致；能读出 70 mm 行程版本。

### 3. 「实机NERO调试 → 夹爪」页
- **状态**：大号开口读数和条形图、力读数、使能 / 归零灯、六个故障灯（电压过低、电机过热、驱动过流、驱动过热、传感器异常、驱动错误）、反馈频率。
- **操作**：目标开口（滑块 + 输入框）、力度（0.5–3.0，轻 / 中 / 重）、张到最大、夹紧、失能、清除故障、物体预设（鸡蛋 / 杯子 / 方块）。
- **① 校正归零**：一个按钮走完 5 步：检查连接 → 失能 → 用手把两指合拢到底（点「已合拢」）→ 归零（等夹爪确认）→ 全行程检查（合拢 / 张到最大 / 合拢，读数要是 0 和 70 或 100 mm）。结果保存。
- **② 力控标定**（初期可以不做）：A 空载基线（不需要设备，得出"碰到东西"的阈值）；B 测力计对照（设定值 → 实测 N，至少 2 个点后，任务里要求的牛顿数就按这张表换算成设定值）；C 物体预设（在真实物体上试夹，合适就保存）。
- **③ 示教模式测试**：机械臂在零力拖动时，夹爪还能不能开合（官方文档没写，要真机试一次）。
- **④ J7 控制器限位**：读出控制器原来的 J7 限位 → 写入 ±87° 并读回 → 在示教模式下拖动 30 秒，程序记录 J7 最大角度，告诉你控制器在拖动时**挡不挡**得住 → 可以恢复原来的限位。

### 4. 另外两页
- **Agentic实机任务**：夹爪区顶部是切换框；原装夹爪时显示 连接（CAN）/ 张开 60 mm / 张到最大 / 夹紧测试 / 失能。任务里的开合直接用真实开口 mm，夹紧力按任务要求的 N 换算成 0.5–3.0 的设定值，是否夹住看"停下时还有开口"。**杯子 / 鸡蛋任务的抓取几何还是 SO-101 的，要等第 2 部分**，现在原装夹爪下不要跑完整的杯子 / 鸡蛋任务。
- **Smol VLA实机任务**：空格键 / 夹爪示教按钮驱动原装夹爪（张开 = 张到最大，夹紧 = 默认力度 1.0）；一键准备会连接当前选中的夹爪；实机回放也按原装夹爪开合。

### 第一次上真机的顺序
1. 夹爪接 24 V，CAN 线接好；「实机NERO调试」第 4 步 CAN 流量应看到夹爪 ID 10（0x51A / 0x52A），看到 0x517 / 0x518 是旧的 ID 7 夹爪，不能用。
2. 「实机NERO调试 → 夹爪」：切到 NERO 原装 → 连接。
3. 校正归零（5 步）。
4. 低速空载开合，再夹软东西。
5. 有空时做 ③ 示教模式测试和 ④ J7 限位测试，把结果告诉我。

### 关于 ArUco
支架侧板是 40 × 40 mm。ArUco 识别需要黑框外有一圈白边，所以程序里填的 ArUco 尺寸是**黑色方块的边长**（不是整张贴纸）。在「Camera调试」的手眼标定处按实际黑框尺寸填写。

- 测试：新 `tests/test_v4_8.py`（8 项）、`tests/test_v4_8_gui.py`（G1–G8）。

## V4.7.3

**V4.7.3**（Smol VLA 实机任务页：Episode 列表文字重叠、录像回放黑屏 / 不动、开始录制前先到 ready_to_work）

### 1. Episode 列表行与行文字重叠
- 原因：这个表用的是 ttk 默认行高（固定像素），你的屏幕有缩放，中文字比行高高，于是叠在一起。程序里其它表格用的是共用样式（行高 = 字体行高 + 8），这个新表漏了。
- 现在：用同一个共用样式。

### 2. 回放录像：先黑屏，然后只有一张静止图
- 原因：开着「YOLOE 标签」时，每一帧要跑两次 YOLOE（主相机 + 腕部相机），比视频的 50 ms 一帧慢得多。旧播放器算完一帧时，只有"还是当前这一帧"才画，可播放已经走到后面了，所以**每一帧都被丢掉**，画面一直是黑的；播到最后停下来，才画出最后一帧（静止图）。一开始的黑屏，是第一次调用 YOLOE 要加载模型。
- 复现：同一段 60 帧录像，旧播放器开 YOLOE 时播放过程中只画了 **1 帧**；关掉 YOLOE 能画 59 帧。
- 现在：视频和 YOLOE 分开跑。视频按 20 帧/秒照常播放，不等 YOLOE；YOLOE 跟得上多少算多少，标签画在当前帧上（最多晚 2 帧）。暂停时显示这一帧自己的标签。第一次加载模型时旁边会提示"YOLOE 计算中（第一次要加载模型）…"。测试：YOLOE 慢 5 倍时，60 帧画出 59 帧。

### 3. 开始示教录制前，先到 ready_to_work
- 实机后端点「开始示教录制」会先问：**机械臂是否先进入 ready_to_work 位姿？**
  - 是：以 10% 速度移过去（和「回放 Episode」移到起点用的是同一个函数），到位后进入示教模式，开始录制。
  - 否：就在当前位置进入示教模式，开始录制（和以前一样）。
  - 取消：不录制。
  - 没移到位（规划失败、急停等）：不进示教模式，也不录制，日志说明原因。
- 位姿：J1–J7 = −0.2, 21.6, −0.1, 61.2, 0.1, 0.2, 44.8°（你截图里的）。新版本自带 `config/real_poses.json`，所以「实机NERO调试」的姿态库里也能看到 `ready_to_work (用户)`。以后在姿态库里用同名 `ready_to_work` 重新保存，就会用新的位姿。
- 注意：移动时控制权会切到 teleop 并允许控制，和「回放 Episode」一样。

- 测试：新 `tests/test_v4_7_3.py`、`tests/test_v4_7_3_gui.py`（K1 行高、K2 慢 YOLOE 下的回放、K3 是 / 否 / 取消 / 移动失败）。
- **没有在真实硬件上运行过。**

## V4.7.1

**V4.7.1**（修复：腕部相机内参每次启动都被丢掉，导致腕部标定每次都要重做）

### 原因
- 程序启动连接腕部相机时，会检查保存的内参是不是"旧的 130° 广角镜头"的（V3.88 加的保护）。判断条件里有两条按畸变参数判断：|k1| > 0.20，或者 8 参数模型里有高阶系数大于 0.15。
- 可是「内参标定」页默认用的就是 8 参数模型，它的高阶系数本来就常常这么大。所以你**刚标好的 4MP 内参，每次启动都被当成旧镜头丢掉**，换成了理论值（焦距 = 0.55 × 画面宽度）。你实测的焦距是 1452.7 px = 0.76 × 画面宽度，两者差了 27%。
- 日志里每次都有这一行，就是这个问题：`[V3.88 wrist] 检测到旧 130° 广角镜头内参 (fx/w=0.77, k1=0.05) … 已自动隔离`。
- 内参一换，之前用正确内参做的腕部手眼标定就对不上了，所以每次重启都要重新标定。

### 修复
- 现在只看**焦距**来判断（130° 镜头的焦距只有画面宽度的 0.35–0.41 倍），以及文件里记录的相机型号。文件记录为 4MP 相机的内参一律保留。
- 真正的 130° 镜头内参仍然会被挡住，提示里会告诉你去重新标定内参。

### 你需要做一次
1. 用 V4.7.1 启动后，日志里**不应该再出现**"检测到旧 130° 广角镜头内参"。
2. 你这次保存的内参（`config/wrist_intrinsics.json`，RMS 0.583 px）可以直接用，不用重做。只需**再做一次腕部手眼标定并保存**，以后重启就不用再做了。

**V4.6.3**（热修复：V4.6.2 执行鸡蛋任务时控制台闪退）

### 这次闪退查到了什么
- `logs/crash.log`：`Fatal Python error: Aborted`，发生在**主线程**里 Tk 刷新「工作区安全」状态标签的 C 代码中（`NERO_V316 _status → configure`）。当时任务线程正在等机械臂下探到位，其他线程是两个相机采集、子进程输出读取和 CAN 监控，**崩溃那一刻都没有在操作界面**。
- 这是 C 层的 abort（不是 Python 异常）。Tcl / Xlib / glibc 在 abort 前会往终端打印一行真正的原因，但这一行以前**只出现在终端上**，`crash.log` 和 `console.log` 里都没有，所以现在还不能百分之百确定是哪个库。
- 用"探针"把所有 GUI 测试重跑了一遍，记录每一个**不在主线程**发起的 Tk 调用：发现实机管线、示教、关节运动等工作线程会通过 `real_cfg()` 直接读「实机NERO调试 → 参数」里的输入框（CAN 口、速度、固件等）。这种跨线程读取要排队等主线程；测试里还复现了它会卡住（主线程等工作线程时，工作线程的这次读取 5 秒都没返回）。这不是这次崩溃那一刻的直接原因，但属于同一类风险。之前 V4.5 那次启动时的段错误也发生在 Tk 的 C 代码里。

### 修改
1. **`real_cfg()` 只在主线程读界面**：工作线程拿到的是主线程最近一次的快照（每次轮询刷新，启动任务前也刷新）。重跑探针：实机任务、示教、关节控制路径上已经**没有任何跨线程 Tk 调用**（只剩冻结的 Camera 模块里手眼标定读标记设置的一处，不在任务路径上）。
2. **创建 Tk 窗口前调用 `XInitThreads`**：Xlib 变成线程安全的，任何第二个线程碰到 X 连接都不会再把进程 abort（`[xcb] Unknown sequence number … Assertion failed` 这一类）。libX11 1.8 起默认就这样做，Ubuntu 22.04 带的是 1.7.5。可用 `NERO_NO_XINITTHREADS=1` 关闭。
3. **X 错误不再让控制台消失**：你点「Smol VLA实机任务」那次闪退，crash.log 里**什么也没有**。这说明进程不是被信号杀死，而是 Xlib 遇到 X 错误后直接 `exit(1)`：这种退出只会在终端打几行字，faulthandler 抓不到（已在虚拟显示器上复现这种"无痕退出"）。V4.6.3 在创建窗口前装上自己的 X 错误处理：错误写进 `crash.log`（类型、请求号；请求号 139 = 字体 / 文字绘制），**控制台继续运行**。正常关闭时 crash.log 末尾会写 `console closed normally`，所以以后能分清是正常关闭、X 错误、abort 还是被系统杀掉（没有任何记录 = 被杀，例如内存不够）。
4. **C 层错误信息落盘**：`start_nero.sh` 把控制台的 stderr 同时写到终端和 `logs/stderr.log`（进程 abort 时也保留，已验证），并设置 `LIBC_FATAL_STDERR_=1`（glibc 的内存错误信息也进 stderr）；超过 5 MB 时转存为 `stderr.prev.log`。`crash.log` 开头会写一行 `XInitThreads ok`。

   - 桌面高度取“相机拟合桌面”和“安全区 z_table”中**更高**的那个；两者差超过 15 mm 时拒绝夹蛋（说明手眼标定或安全区桌面高度有问题），日志 `[FAIL] [V4.5 EGG PLAN] 相机测得的桌面比安全区 z_table …`。

   - 规划时按执行时同样的直线插值点检查关节余量（V4.4 只查两端，曾出现“规划通过、执行时 J6 余量 3.9° 被拒”）。
